# Resolver

The notification system uses a Resolver in its routing sub-system to determine
exactly which users should receive a Message, as determined by its Topics.

The Resolver is not concerned with how a Message is delivered to a user; only
with whether a Message is deliverable to a user.


## Glossary

<dl>
  <dt>Resolver</dt>
  <dd>
    A subsystem that is used to determine which users are subscribed to a
    Message Topic.
  </dd>

  <dt>Message</dt>
  <dd>
    A payload that has been generated by another subsystem. It has one or more
    Topics.
  </dd>

  <dt>Topic</dt>
  <dd>
    A channel on which a message is to be broadcast.
  </dd>
</dl>


## Implementation

The resolver is implemented as a [trie](https://en.wikipedia.org/wiki/Trie)
data structure.


### Keys

The keys in the trie are in the same format as a Message's Topic.

> In theory, a Message may have more than one Topic; any user who's subscribed
  to any of these Topics will receive the Message.
>
> In practise, a Message is only ever assigned a single Topic.

#### Format

Example Message Topic:

`info.notify.service.1.43.1.forum.77.replied`

Words in a Message Topic are delimited by `.` characters. Each node (whether a
leaf or branch) within the trie is a single word.

#### Wildcards

A trie node may also be one of these wildcard values:
* `*` matches any single word in the Topic
* `#` matches zero or more words in the Topic

#### Examples

The following trie keys will match the above example Topic:
* `info.notify.service.1.43.1.forum.77.replied`
  * this is an exact match for the Topic
* `info.notify.service.1.43.1.forum.*.replied`
  * the wildcard `*` word matches `77`
* `info.notify.service.1.43.1.#`
  * the wildcard `#` word matches everything after it
* `info.notify.service.1.43.1.forum.77.replied.#`
  * the wildcard `#` word matches the end of the key

The following will not match:
* `info.notify.serviced.1.43.1.forum.77.replied`
  * `serviced` doesn't match the word `service`
* `info.notify.service.2.43.1.forum.77.replied`
  * `2` doesn't match the word `1`
* `info.notify.service.1.43.1.blog.#`
  * Despite the `#` wildcard, `blog` doesn't match the word `forum` beforehand


### Values

Each value in the trie is a list; each item in that list will be one of either:
* an integer (corresponds to a user ID)
* a string (this key is aliased to another key in the trie)

The final value will be the recursive union of:
* the integer values
* any integer values returned by resolving an alias key

#### User IDs

An integer value is treated as a user ID: this means that this user is
subscribed to this Topic.

#### Aliases

A string value is treated as an alias to another trie key: when the Resolver
sees an alias, it recursively looks up the value stored for that key, and
returns all users which that value resolves to.

The Resolver will throw an error if it detects circular references.

#### Examples

Looking up the key `info.notify.service.1.43.1.forum.77.replied` in the data
structure below:

```
{
    "info.notify.service.1.43.1.forum.77.replied": [
        1,
        3,
        6,
        10,
        "info.notify.service.2.43.1.forum.77.replied",
        "info.notify.service.2.43.1.forum.76.replied",
    ],
    "info.notify.service.2.43.1.forum.77.*": [
        1,
        3,
        9,
        15,
    ],
    "info.notify.service.3.43.1.forum.77.*": [
        11,
        19,
    ],
}
```

returns the following:
* users `[1,3,6,10]`
* any user found by looking up the key
  `info.notify.service.2.43.1.forum.77.replied`
  * this recursive lookup returns `[1,3,9,15]`
* any user found by looking up the key
  `info.notify.service.2.43.1.forum.76.replied`
  * this recursive lookup returns nothing
* the union of these values is returned: `[1,3,6,9,10,15]`

> Note that this example shows the write-optimized variant of the resolver's
  data structure.
>
> The write and read optimized variants are functionally identical, but are
  intended for different use cases.


### Variants

The Resolver has two variants, for two different use cases:
* read performance
* writeability

The read performance and writable variants are able to be translated to one
another.


#### Read-only (hydrated)

This variant is optimised for read performance: it is implemented as the nested
Trie structure as documented above.

Each word in the key is a single node in the trie, with the following
optimizations:
* Numeric words are replaced with the regular expression `(\d+)`, capturing the
  word for later comparison. Once the last word in the key is traversed, the
  captured numeric keys are traversed from that point.
* Single wildcard words (`*`) are replaced with the regular expression
  `[^\.]*`, matching any single word
* Wildcard sentences (`#`) are replaced with the regular expression `.*`,
  matching any character string

```
{
  info: {
    notify: {
      service: {
        "(\d+)": {
          "(\d+)": {
            "(\d+)": {
              forum: {
                "(\d+)": {
                  replied: {
                    // at this point, matches for "info.notify.service.(\d+).(\d+).(\d+).forum.(\d+).replied"
                    // are evaluated
                    1: {
                      43: {
                        1: {
                          // matches "info.notify.service.1.43.1.forum.77.replied"
                          77: [ 1, 3, 6, 10, "...", "..." ]
                        }
                      }
                    }
                  },
                  "[^\.]*": {   // this non-capture is intentional, which is why there's no nested key for it
                    2: {
                      43: {
                        1: {
                          // matches "info.notify.service.2.43.1.forum.77.*"
                          77: [ 1, 3, 9, 15 ]
                        }
                      }
                    },
                    3: {
                      43: {
                        1: {
                          // matches "info.notify.service.3.43.1.forum.77.*"
                          77: [ 11, 19 ]
                        }
                      }
                    }
                  }
                }
              }
            }
          }
        }
      }
    }
  }
}
```

A read operation in this data structure should be (one or more) O(1) efficiency
hash lookups.

However, a write operation will be somewhat more expensive than the writable
variant: the key must be split into its constituent words before the lookup can
take place.

##### Use cases

The read-only variant is used in the routing sub-system; its resolver is used
for determining the target audience for a message.


#### Writable (flattened)

This variant is optimised for writeability: it is a 2-dimensional array.

The entire key is used as the key for the array.

```
{
    "info.notify.service.1.43.1.forum.77.replied": [
        1,
        3,
        6,
        10,
        "info.notify.service.2.43.1.forum.77.replied",
        "info.notify.service.2.43.1.forum.76.replied",
    ],
    "info.notify.service.2.43.1.forum.77.*": [
        1,
        3,
        9,
        15,
    ],
    "info.notify.service.3.43.1.forum.77.*": [
        11,
        19,
    ],
}
```

A write operation in this data structure should be a simple O(1) efficiency
hash lookup.

However, a read operation will be significantly more expensive (to the point of
being infeasible), and is at least an O(n) operation: each key in the data
structure must be evaluated against the looked-up key, and determined whether
it is a match for that key (all the while evaluating any wildcard characters in
key names).

##### Use cases

The writable variant is used when rebinding the routing sub-system's resolver;
the rebinding process must incrementally build a new data structure, and this
process involves repeated writes to the data structure.

Once the binding is complete, the writable data structure is translated to a
readable structure and cached for the resolver to use.


### Rebinding

> TODO figure out why rebinding happens only upon update, rather than create?

Any action within Schoolbox that changes the audience of a topic must rebind
the associated values stored within the resolver.

These actions include:
* Changing the alternate source of a component
  * in order to notify users on the component's folder when the source
    changes, all redirects must be updated
* Changing a user's access to a folder
  * in order to determine which routes a user is subscribed to, all of their
    routes must be recalculated
* Importing users
  * all imported users must be rebound
