# Spiking a Ticket

A spike (technical or otherwise) is preparation work to be undertaken on a Story, Task or Epic with the intended purpose
of making it ready for a Backlog Refinement session. To be considered "ready for refinement", it needs to contain enough
detail that any seasoned Schoolbox Developer could read the description and associated documentation and understand the
scope of work with no additional input from the author, collaborators or any external dependencies. 

In a lot of ways, a spike is the solo reconnaissance mission variant of refinement, which is done co-op with the entire 
team.

## What a Spike Isn't

* A spike isn't coding.
* It's not ironing out absolutely every final tiny minutia - developers are capable of problem-solving.
* You don't _necessarily_ need to completely solidify the Acceptance Criteria; making a start is great, but AC can be
  fleshed out and finalised as part of the refinement session as a collaborative effort.

## Discover and Explore

If a ticket relates to UI in any way, chances are high that the spike will involve one or more UX activity. These don't
have to be undertaken exclusively by the UX Guild; you can do it too! Whether it's performing some Discovery, or you're
whipping up some rapid prototyping, all of this exploration is valuable in figuring out what will or won't work when it 
comes to making UI changes. Chat to the UX Guild for more information on the kinds of things you can do to make a UI
ticket Ready. 

## Assume Nothing!

Critical thinking is essential to a spike. Every assumption you make needs to be noted and either left for consideration
for the developer who ultimately does the work, or for you to resolve and document. What are the implications of what's 
proposed in the ticket? Are there technical constraints? What foreseeable pitfalls are there? What **don't** we know??

If there are external dependencies, try your utmost to resolve them. That means obtaining things like API keys, external
URLs, etc. so that, when the ticket hits the Sprint it's able to be done without being held up by having to go hunting 
for resources (whether that be humans or services). 

If an external dependency on a human cannot be resolved (ie. the developer will need to liaise while the ticket is under
active development), ensure that contact details are provided on the ticket.
